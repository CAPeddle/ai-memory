## Deferred / Open Questions

### From 2026-08-28 review

- **The spike tests only row-level security, never the explicit-WHERE alternative it claims to decide between** — 05-02, DECISION-01 mechanism (P1, adversarial and adversarial-codex cross-model, confidence 100)

  The consequence: ADR-018 will pick the mechanism that roughly 15 enforcement sites in Phases 6-9 are built on, and that decision is costly to reverse, on the strength of a one-armed experiment. A passing spike proves RLS *can* implement the visibility matrix. It does not show RLS is simpler, safer, or easier to audit than per-query `WHERE` predicates, because the alternative is never built or measured. Options: add a minimal explicit-`WHERE` prototype on one path so both arms are exercised, or have ADR-018 say plainly that only RLS was tested and the `WHERE` path is an unvalidated contingency. This is a real scope trade-off, not a mechanical fix.

- **If the spike disqualifies RLS, nothing in the plan builds the documented `WHERE`-clause fallback** — 05-02 Task 2, ADR-018 mechanism decision (P1, adversarial-codex cross-model, confidence 75)

  The consequence: an executor who hits the fallback branch finishes the phase with an ADR naming a mechanism that has no helper, no downstream enforcement contract, and no test. Implementers would have to invent that work after the plan claims completion. The tasks as written only create and verify the scoped-transaction helper and the RLS artifacts. No fix was proposed; deciding whether the fallback needs its own task, or triggers a re-plan, is open.

- **Background workers and write paths are missing from the Phase 6 RLS rollout contract** — 05-02 Task 1, Phase 6 RLS enablement (P1, adversarial-codex cross-model, confidence 75)

  The consequence is silent breakage at the production cutover. The spike's policy carries no command qualifier, so it also governs `INSERT`, `UPDATE`, and `DELETE`. When RLS is enabled, any path that runs without a declared scope sees no rows and cannot write. That includes the consolidation worker's promotion step, the entity and embedding workers, and `capture_thought` itself, so background promotion could simply stop. Phase 6 needs a contract that lists per-command policy behaviour, an authorised execution context for cross-scope workers, and tests of those paths under forced RLS before enablement. This belongs in Phase 6 planning.

- **Migration and RLS-spike tests mutate the same test database the long-running test server uses** — Plans 05-01 and 05-02, migration and spike tests (P1, adversarial-codex cross-model, confidence 75)

  The consequence is flaky or misleading results. The migration tests temporarily drop the `policy_scope` column inside a rollback transaction, and the spike enables forced row-level security on the real `thoughts` table. Both run against the shared test database while the long-running test server and its background workers keep querying it. Those workers can hit denied queries or a missing column, or mutate fixtures mid-run, so an experiment can fail for reasons unrelated to the mechanism under test. The alternative is a third, disposable database with no long-running clients, which is a test-infrastructure decision beyond this phase. Mitigations already in the plans: the spike's filtering only applies to its own non-superuser role (the app's superuser role is unaffected), and every mutation is torn down in `finally`.

- **ADR-018's exact-path check contradicts the plan's own renumbering escape hatch** — 05-02 Task 2, ADR-018 filename (P2, coherence, confidence 100)

  The consequence is an unresolvable instruction for an autonomous executor. Task 2's reading list says that if another branch has already claimed ADR-018, the executor should take the next free number. Its acceptance criteria and automated verify still hard-code the `ADR-018-...` path, so the sanctioned outcome fails verification. Two fixes are on the table: make the check read the filename recorded in the SUMMARY, or drop the escape hatch and halt on a collision. Neither has been chosen.

- **The spike queries the table directly rather than through a real retrieval path** — 05-02 Task 1, spike realism (P2, product-lens, confidence 75)

  The consequence: integration quirks surface in Phase 6, not here. Decision D-04 and roadmap success criterion #2 frame the spike as "against one real query path" (`list_thoughts` was suggested). The plan instead seeds rows and issues raw `SELECT`s through the helper. The research notes treat this as the correct reading, because the commit-and-teardown design is what exercises real pool checkout. Even so, a connection-handling quirk in the real handler (sequential queries, its own transactions) would not show up until Phase 6 wires it in. No fix was proposed.

### From 2026-09-25 review

- **Production cannot use RLS until the application stops connecting as a superuser** — 05-02 Task 1 / ADR-018 (P1, found while completing the P0 superuser fix, confidence 100)

  The consequence: enabling RLS in Phase 6 as things stand would be a silent no-op, with every query still seeing every row. Still open: who introduces a non-superuser runtime role, and when (in Phase 6, or as a prerequisite story), and how migrations and the AGE extension load, which may still need elevated rights, are split off from it.
