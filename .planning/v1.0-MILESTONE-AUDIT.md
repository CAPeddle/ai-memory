**Producer/consumer contract, Phase 2 hub ↔ Phase 3 client — zero drift.** Register path,
events path, `Authorization: Bearer <64-hex>`, `X-Node-Enrolment-Secret`, the `{node_id}` 201
response, the `{acknowledged: [{client_seq, event_id}]}` 200 response, and the 400
`issues[].client_seq` rejection shape all match field for field. The `bigint`→string hazard is
handled at the boundary (`store.ts:983 Number(r.client_seq)`) and asserted without coercion at
the test site.

**The non-obvious correctness point worth preserving:** the ack is re-derived by `SELECT`
(`store.ts:1117`), not taken from the INSERT's `RETURNING`. An ack built from `RETURNING` would
omit exactly the replayed rows, and the node would retry them forever. Documented at
`004_run_events.sql:16-20`.

## The one finding that justifies running this audit

**W3 — the `FEATURE_WORKFLOW` disposition was routed to Phase 4 and Phase 4 never received it.**

Phase 3's plan 03-01 hardcoded `FEATURE_WORKFLOW: "true"` on the base `mcp` service
(`docker-compose.yml:58`), which combined with `3000:3000` published on all interfaces (`:67`)
makes `GET /workflow` answer **200 unauthenticated** — the dashboard shell at
`server/index.ts:1262` carries no middleware, unlike `:1212` and `:1252`. Phase 3 surfaced this
honestly and routed the decision forward: `03-VERIFICATION.md` lists it as human item 3, and
`story-board.md:969` says "Phase 4 owns it". Phase 4's ROADMAP entry carries two explicit
"Carried forward" items and this is not among them. `ADR-016:184` dispositions the flag's
*existence* ("stays until an extraction plan retires them") — not the unauthenticated-shell
exposure.

No data leaks: the shell fetches only the authenticated `/api/workflow` API, which correctly
answers 401. So this is a warning, not a blocker. But it is a **standing production-shaped
exposure that no one has signed off**, and it would have closed silently had this milestone been
archived without an audit.
