# fix: Address ST-047 review findings

## Summary

Close the ST-047 review findings with the smallest safe remediation: correct misleading MCP tool metadata, tighten the metadata test without brittle duplication, restore the required ExecPlan/board governance trail, and clean or ignore local runtime byproducts so the branch is reviewable as one story.

---

## Problem Frame

The ST-047 implementation achieved the core tool-description work, but review surfaced inconsistencies between metadata and runtime behavior, missing workflow artifacts, stale board state, unrelated branch artifacts, and local byproducts that could contaminate the PR.

---

## Requirements

- R1. Fix every review finding with the least behavioral change possible.
- R2. Keep ST-047 metadata implementation narrow: no handler logic changes, no schema cardinality changes, no new tool names, and no broad refactors.
- R3. Make MCP tool descriptions accurate for existing runtime behavior, especially context/profile handling and search fallback behavior.
- R4. Keep the `tools/list` metadata test meaningful without maintaining a duplicated hard-coded tool list that can drift.
- R5. Add the missing ST-047 ExecPlan artifact and synchronize board state with the implemented/reviewed story.
- R6. Remove unrelated branch noise from the ST-047 review scope and handle local runtime byproducts deliberately.
- R7. Preserve isolated Deno verification through `mcp-test` with `--frozen`.

---

## Scope Boundaries

- Do not implement profile filtering, strict project behavior changes, consolidation annotation changes, or runtime handler changes in this remediation unless a test proves current behavior is broken. The minimal fix is to make metadata match current behavior.
- Do not delete user-created untracked files blindly. Either leave them untracked and excluded, move them to the proper story, or ignore generated byproducts where appropriate.
- Do not carry unrelated workflow/solution docs in the ST-047 PR unless they are intentionally part of this remediation and pass link/frontmatter checks.
- Do not run a whole-file formatting churn pass if it rewrites unrelated code. Prefer targeted formatting or accept current style when repository formatting is already drifted.

### Deferred to Follow-Up Work

- Implementing true profile filtering for `search_thoughts` or `list_thoughts`: separate behavior story because it changes search/list semantics.
- Adding MCP annotations to `consolidate`: separate tool-safety story unless the PO decides metadata-only ST-047 should include annotation changes.
- Fixing unrelated pre-existing worker/consolidation TypeScript errors that block the full suite.
- Full server-suite verification is optional/non-gating for this remediation because known unrelated blockers exist; the required gate is the focused MCP protocol compatibility test plus diff/review checks.

## Key Technical Decisions

- Prefer metadata correction over runtime behavior changes: review findings are about misleading agent-facing descriptions, not proven behavior defects.
- Derive audited tool names from existing code/server metadata rather than a new test-only full list: this addresses both deletion-escape and duplication-drift concerns.

- Treat generated local byproducts separately from source artifacts: ignore or remove `.server.log`, `.server.pid`, and disposable review output, but do not auto-delete scripts or docs that may be intentional work from another story.

## Implementation Units

### U1. Correct misleading MCP metadata

**Goal:** Make tool descriptions match current runtime behavior without changing handlers.

**Requirements:** R1, R2, R3

**Dependencies:** None

**Files:**
- Modify: `server/index.ts`
- Test: `server/tests/mcp-protocol-compat.test.ts`

**Approach:**
- Update `search` edge-case wording so nearest-neighbor fallback behavior is accurately described instead of promising empty results for all empty matches.
- Update `search_thoughts` context wording to explain that project context boosts by default and only filters when `strict` is present; avoid claiming profile filtering.
- Update `list_thoughts` context wording to say the current list filter is project-based; remove profile examples unless the implementation actually filters by profile.
- Do not add `consolidate` annotations in this unit; that changes protocol metadata beyond description text and is deferred unless explicitly pulled in.

**Patterns to follow:**
- Existing inline `server.registerTool` metadata in `server/index.ts`.
- Existing `parseContext` behavior and current SQL predicates in `search_thoughts` / `list_thoughts`.

**Test scenarios:**
- Happy path: `tools/list` still returns descriptions satisfying the metadata quality audit.
- Error path: context-related descriptions no longer imply profile isolation that runtime does not provide.
- Regression: no handler logic, SQL predicates, annotations, or input schema requiredness changes appear in the diff.

**Verification:**
- Focused protocol test passes after metadata wording updates.
- Diff inspection confirms metadata-only changes for this unit.

### U2. Make metadata tests drift-resistant without hard-coded duplication

**Goal:** Ensure the test audits the real registered tool surface while avoiding a second full manually maintained tool list.

**Requirements:** R1, R4

**Dependencies:** U1

**Files:**
- Modify: `server/tests/mcp-protocol-compat.test.ts`
- Reference: `server/index.ts`
- Reference: `server/tests/_helpers/mcpClient.ts`

**Approach:**
- Keep semantic metadata checks for usage, parameters, examples, returns, and error/edge-case guidance.
- Compare `tools/list` to `server-info.toolNames` so the public compatibility metadata remains synchronized.
- Add an independent guard that derives registered tool names from `server/index.ts` source text, or another low-risk source-of-truth check, and compares that set to `tools/list` / `server-info`. Resolve the source path from the test module, such as `new URL("../index.ts", import.meta.url)`, so it works inside the `mcp-test` container where `server/` is mounted at `/app`.
- Add targeted regression assertions for the specific review findings, not only generic description quality: `search` must describe nearest-neighbor fallback without promising empty results for every no-match case; `search_thoughts` must describe project boost/default behavior and strict project filtering accurately; `search_thoughts` and `list_thoughts` must not imply profile filtering/isolation unless runtime behavior changes.
- Keep test assertions structural and semantic, not exact prose.

**Patterns to follow:**
- Existing `resultOf` and `mcpRequest` helpers in `server/tests/mcp-protocol-compat.test.ts`.
- Existing test permissions include `--allow-read`, so reading `server/index.ts` is acceptable for this focused compatibility test when resolved with a container-safe module-relative URL.

**Test scenarios:**
- Integration: `tools/list` and `server-info.toolNames` expose the same tool names.
- Integration: every `server.registerTool` name in `server/index.ts` appears in `tools/list` and receives metadata quality assertions.
- Regression: `search` metadata mentions fallback behavior and does not state that all empty matches return an empty array.
- Regression: `search_thoughts` metadata documents project boost/default behavior plus strict filtering, and does not claim profile filtering/isolation.
- Regression: `list_thoughts` metadata documents project-based filtering and does not claim profile filtering/isolation.
- Edge case: no-parameter tools still require explicit no-argument guidance.
- Edge case: schema properties with blank descriptions fail.

**Verification:**
- Removing a registered tool from metadata or server-info would fail the test.
- Adding a new `server.registerTool` without a useful description would fail the test.
- Reintroducing the reviewed misleading metadata claims would fail the targeted regression assertions.
