# Software Requirements Specification — ai-memory

**Version:** 1.1  
**Date:** 2026-05-15  
**Status:** Active

---

## §1. Purpose

This document specifies the functional and non-functional requirements for **ai-memory** — a personal, local-first AI memory service. It is the authoritative source of "what the system must do" and governs implementation decisions in all stories and ExecPlans.

Every functional requirement (FR) and non-functional requirement (NFR) defined here shall be traceable to at least one backlog story or investigation document.

---

## §2. Scope

**ai-memory** is a personal knowledge management and AI context service. It consists of:

1. **The Brain** — A core memory engine that ingests, stores, retrieves, and consolidates knowledge across three tiers (Shards, Wiki, Views).
2. **REST API** — An HTTP interface for programmatic interaction with the Brain.
3. **MCP Server** — A Model Context Protocol facade over the Brain, consumed directly by AI agents (GitHub Copilot, Claude, etc.).
4. **View Projectors** — Synthesis services that produce stateful Markdown projections over the Brain (Storyboard, Wiki).

The system serves:
- A **solo developer / knowledge worker** (personal use only — the primary human user)
- **AI agents** (GitHub Copilot, Claude, and other MCP clients) consuming memory via MCP and REST
- **Developer tooling** (CLI, VS Code extensions) interacting via REST

### Out of Scope (v1.0)

- Multi-user or team collaboration
- Mobile clients or voice interface
- Real-time event streaming (WebSocket / SSE)
- Cloud-hosted deployment as a service
- Authentication and authorisation (deferred to multi-user phase)

## §3. Definitions and Terms

| Term | Definition |
|------|-----------|
| **The Brain** | The core memory engine — the persistent store of all knowledge. It is the source of truth; views are projections over it. |
| **Shard** | An episodic memory — a raw, timestamped unit of input (transcript, commit message, observation, brainstorm). Shards are ingested and stored without curation. |
| **Wiki** | A view over The Brain — a curated, synthesized projection of semantic knowledge for a project or domain. Generated by the Synthesis Service. |
| **Storyboard** | A view over The Brain — a stateful task board projection (professional or personal) showing goals, stories, and their execution state. Machine-readable via REST/MCP; optionally rendered as Obsidian Markdown. |
| **Semantic memory** | An evergreen fact — a promoted, curated piece of knowledge that does not decay. Equivalent to Tier 2 "Wiki" knowledge. |
| **Episodic memory** | A raw session-scoped observation — an ingested Shard. Candidates for consolidation into semantic memory. |
| **Consolidation** | The automated process of promoting qualifying episodic memories to semantic memories via scoring. Equivalent to the "Janitor Agent" in the conceptual model. |
| **Hybrid search** | The two-lane retrieval pipeline: BM25 (lexical via FTS5) + Vector (semantic via embeddings), fused via Reciprocal Rank Fusion (RRF). |
| **Structural pre-filter** | A query constraint (entity / project / relationship scope) applied before hybrid search ranking, narrowing the candidate set without competing as a ranking signal. |
| **RRF** | Reciprocal Rank Fusion — a rank-fusion formula: `RRF_score(d) = Σ 1/(k + rank_i)`, k=60. Fuses BM25 and vector rankings without score normalisation. |
| **MMR** | Maximal Marginal Relevance — a re-ranking technique: `MMR = argmax[λ·sim(d,q) − (1−λ)·max(sim(d,selected))]`, λ=0.7. Reduces near-duplicate results. |
| **View** | A stateful projection over The Brain. Both the Wiki and the Storyboard are views. Views are not separate storage; they are derived and rendered on demand or via synthesis triggers. |
| **Synthesis trigger** | A domain event fired after a memory write, which invokes `ISynthesisService.UpdateViewsAsync()` to refresh affected views. |
| **IMemoryStore** | The repository abstraction that decouples the memory engine from any specific storage backend (SQLite, PostgreSQL). |
| **LLM client** | The abstraction over language model providers (OpenAI, Anthropic/OpenRouter, Ollama) used for embedding generation and synthesis. |
| **ULID** | Universally Unique Lexicographically Sortable Identifier — used as the primary key type for all memory records. |

## §5. Functional Requirements

Requirements use the convention: `[FR]-[category]-[number]`. Categories: **I** (Ingest), **R** (Recall/Search), **M** (Memory management), **C** (Consolidation), **V** (Views/Synthesis), **B** (Storyboard), **API** (REST API), **MCP** (MCP interface), **P** (Project), **H** (Health/System).

---

### 5.1 Memory Ingest

**FR-I-001** The system shall accept semantic (evergreen fact) memories with the following fields: `content`, `project?`, `tags?[]`, `source?`, `confidence?`.

**FR-I-002** The system shall accept episodic (raw session observation) memories with the following fields: `content`, `session_id`, `project?`, `tags?[]`, `agent_context?`.

**FR-I-003** The system shall generate a vector embedding for every ingested memory using the configured `IEmbeddingService` (default: OpenAI `text-embedding-3-small`, 1,536 dimensions).

**FR-I-004** The system shall deduplicate memory on ingest by computing cosine similarity against existing embeddings. Memories with cosine similarity > 0.95 to an existing active record shall be rejected with a `409 Conflict` response.

**FR-I-005** The system shall assign a ULID primary key to every memory record at ingest time.

**FR-I-006** The system shall infer the `project` field from file paths, build system markers (e.g., `CMakeLists.txt`, `.csproj`), or package references if not explicitly supplied.

**FR-I-007** The system shall fire a domain event after each successful memory write, which can trigger view synthesis asynchronously.

**FR-I-008** The system shall allow batch ingest of multiple memories in a single API call (up to 100 records per request).

**FR-I-009** The system shall log every ingested memory with a creation timestamp (ISO 8601, UTC).

**FR-I-010** The system shall support a `source` attribution field with three values: `user-taught`, `auto-promoted`, `observed`.

---

### 5.2 Recall and Search

**FR-R-001** The system shall implement a two-lane hybrid search pipeline: BM25 (FTS5) + Vector similarity (embedding cosine), fused via RRF (k=60).

**FR-R-002** The BM25 lane shall use FTS5 with the following query capabilities:
- Phrase matching (`"exact phrase"`)
- Prefix queries (`term*`)
- Boolean operators (AND, OR, NOT)
- Column-filtered search (`content:term`)
- NEAR operator for proximity matching

**FR-R-003** The vector lane shall perform approximate nearest-neighbour search using the query embedding against stored embeddings, returning ranked results by cosine similarity.

**FR-R-004** The system shall apply structural pre-filtering before hybrid search when entity/project/relationship constraints are specified. Structural data narrows the candidate set; it does not participate as a ranking signal in RRF.

**FR-R-005** The system shall apply MMR re-ranking (λ=0.7) to the RRF-fused result set to reduce near-duplicate results.

**FR-R-006** The system shall apply project boosting: same-project results receive a 1.2× relevance multiplier. Cross-project results are not penalised.

**FR-R-007** The system shall support search filter parameters: `project?`, `type?` (semantic|episodic|all), `tags?[]`, `date_range?`, `min_confidence?`, `context?` (ambient scope override — see ADR-008).

**FR-R-016** The system shall support request-scoped ambient context propagation. When a request includes context metadata (project, profile, entity), all operations within that request shall implicitly use that context unless explicitly overridden by a per-call parameter. Ambient context is resolved at service layer entry with precedence: explicit parameter override → ambient context → null (global).

**FR-R-008** The default search limit shall be 10 results; the maximum configurable limit shall be 100.

**FR-R-009** The system shall return a `recall_event_id` with every search result to support the feedback loop.

**FR-R-010** The system shall log every recall event with: `memory_id`, `query`, `query_embedding`, `relevance_score`, `position_in_results`, `recalled_at`.

**FR-R-011** The system shall track `recall_count` and `last_recalled` on each memory record, incrementing on every successful recall.

**FR-R-012** The system shall support keyword-only search (FTS5-only) as a graceful degradation mode when the embedding service is unavailable.

**FR-R-013** The system shall include `score`, `type`, `project`, and `id` in each search result entry.

**FR-R-014** The system shall support entity-based recall: given an entity name, return memories referencing that entity across all projects.

**FR-R-015** The recall response shall include metadata: `total`, `took_ms`, `cursor` (for pagination).

### 5.3 Memory Management

**FR-M-001** The system shall implement soft deletion: deleted memories set `active = false` and are excluded from search; they are retained for audit.

**FR-M-002** The system shall implement a corrections model: correcting a fact creates a new memory with a `supersedes` field referencing the old record; the old record is soft-deleted.

**FR-M-003** The system shall support forced promotion of an episodic memory to semantic memory (`POST /api/v1/memories/:id/promote`).

**FR-M-004** The system shall support `memory_inspect` which returns a memory's full detail including: content, tags, project, source, confidence, recall history, and linked memories (via `supersedes`).

**FR-M-005** The system shall support listing memories with cursor-based pagination (not offset-based), supporting filters: `project?`, `type?`, `tags?[]`, `active?`.

**FR-M-006** The system shall support explicit feedback on recall events: `helpful` or `irrelevant`. Feedback is non-blocking and optional.

**FR-M-007** The system shall record feedback on recall events in the `recall_events` table and use it as input to the consolidation scoring pipeline.

**FR-M-008** The system shall use recency as a tiebreaker only (within ε=0.01 score threshold), never as a decay factor. Stored memories do not lose weight over time.

### 5.4 Consolidation Pipeline

**FR-C-001** The system shall implement a consolidation pipeline that evaluates episodic memories as candidates for promotion to semantic memory.

**FR-C-002** The consolidation scoring formula shall be:
```
score = (0.40 × normalised_frequency) + (0.35 × normalised_diversity) + (0.25 × normalised_relevance)
```
where:
- `frequency` = number of recall events referencing this episodic memory
- `diversity` = number of distinct projects in which it was recalled
- `relevance` = proportion of recall events rated `helpful` vs total feedback

**FR-C-003** The consolidation threshold shall be configurable (default ≥ 0.7). Candidates scoring 0.5–0.7 shall be flagged for manual review.

**FR-C-004** The consolidation pipeline shall run on a configurable schedule (default: triggered manually or via `POST /api/v1/consolidate`). A dry-run mode shall show candidates without acting.

**FR-C-005** The system shall prevent duplicate promotions via content-hash deduplication during the promotion step.

**FR-C-006** All consolidation actions shall be logged to a `consolidation_log` table with: `episodic_memory_id`, `score`, `decision` (promoted | flagged | rejected), `run_at`.

**FR-C-007** The consolidation pipeline shall require a minimum of 2 recall events before a memory is eligible for automatic promotion.

**FR-C-008** The consolidation pipeline shall accept an optional `context_project` parameter to constrain the consolidation run to memories belonging to a specific project. When omitted, consolidation runs globally across all projects. (Phase 4 extension; not required in v1.0.)

---

### 5.5 View Generation and Synthesis

**FR-V-001** The system shall expose an `ISynthesisService` interface that, when invoked, generates or refreshes a named view over the Brain.

**FR-V-002** The synthesis service shall support incremental view updates: it shall track the last-synthesised memory ID per view and only process delta records since that point.

**FR-V-003** The synthesis service shall call `ILlmClient` to produce synthesised view content from a batch of relevant memories.

**FR-V-004** Views shall be written to a configurable output path (default: a directory alongside the database; optionally an Obsidian vault path) as Obsidian-compatible Markdown files with YAML frontmatter.

**FR-V-005** View generation shall be triggered asynchronously by the domain event fired at FR-I-007; it shall not block the memory write response.

**FR-V-006** Every view file shall include YAML frontmatter with: `type`, `generated_at`, `memory_count`, `project?`, `profile?` (professional | personal for storyboard views).

**FR-V-007** The synthesis service shall support disabling per view type via configuration.

---

### 5.6 Storyboard

**FR-B-001** The system shall maintain a storyboard as a stateful projection over The Brain with story records containing: `id`, `title`, `description`, `status` (todo | in-progress | review | done), `priority`, `profile` (professional | personal), `project?`, `tags?[]`, `acceptance_criteria?[]`, `created_at`, `updated_at`.

**FR-B-002** The system shall support CRUD operations on storyboard stories via REST and MCP.

**FR-B-003** An agent shall be able to claim a story by transitioning its status from `todo` to `in-progress`. Only one story per profile may be `in-progress` at a time (WIP limit = 1).

**FR-B-004** A story's `status` shall be a controlled state machine: `todo → in-progress → review → done`. Back-transitions (e.g., `review → in-progress`) shall be permitted.

**FR-B-005** The system shall support querying stories by profile, status, priority, project, and tags.

**FR-B-006** The system shall support rendering the storyboard as an Obsidian-compatible Markdown file (with YAML frontmatter per story + Dataview-queryable properties) via `GET /api/v1/views/storyboard?profile=professional`.

**FR-B-007** Storyboard stories shall be linkable to memories via `memory_ids?[]`, enabling context pull at story pickup time.

**FR-B-008** The system shall provide a layered context model for story pickup: agents first receive the story summary + status, then fetch full details (description, acceptance criteria) on demand.

**FR-B-009** When `story_claim(storyId)` is called, the response shall include the story's resolved context string in the format `project:{slug},profile:{profile}`. This enables the calling agent to pass the context forward to subsequent `memory_search` or storyboard calls without needing to inspect the story record separately.

**FR-MCP-001** The MCP server shall be a thin facade over the shared `IMemoryService` layer; all business logic shall reside in the service layer, not in MCP tool handlers.

**FR-MCP-002** The following MCP tools shall be implemented:

| Tool | Description |
|------|-------------|
| `memory_teach(content, project?, tags?)` | Store a permanent semantic memory |
| `memory_search(query, project?, type?, limit=10)` | Hybrid search with scoring |
| `memory_log_episode(content, sessionId, project?, tags?)` | Record an episodic observation |
| `memory_correct(memoryId, newContent)` | Correct a memory with audit trail |
| `memory_delete(memoryId)` | Soft-delete a memory |
| `memory_list(project?, type?, tags?, cursor?, limit=20)` | List with filters |
| `memory_inspect(memoryId)` | Full detail + recall history |
| `memory_feedback(recallEventId, "helpful"\|"irrelevant")` | Record feedback |
| `memory_promote(episodicId)` | Force promotion to semantic |
| `memory_consolidate(dryRun?)` | Trigger consolidation pipeline |
| `memory_projects()` | List registered projects |
| `memory_stats(project?)` | System or project statistics |
| `story_list(profile?, status?)` | List storyboard stories |
| `story_claim(storyId)` | Transition story to in-progress |
| `story_complete(storyId)` | Transition story to done |

**FR-MCP-003** MCP tool responses shall return formatted text/Markdown rather than raw JSON to optimise for agent consumption.

**FR-MCP-004** The following MCP Resources (Layer 0 — always available) shall be implemented:

| Resource URI | Description |
|-------------|-------------|
| `memory://facts/{project}` | Top 20 most-recalled facts for the project; bullet format; ~500 tokens max |
| `memory://recent-episodes` | Last 10 episodes; one-line summaries grouped by session |
| `memory://stats` | System health, memory counts, consolidation status |

**FR-MCP-005** The MCP server shall support two transports: stdio (for local CLI clients) and HTTP/StreamableHTTP (for Copilot and Claude Desktop).

**FR-MCP-006** `memory_search` results shall include per result: `[Score: X.XX] (type, project) content summary — ID: xxx`.

**FR-MCP-007** The MCP tools `memory_search`, `memory_teach`, `memory_log_episode`, and `story_list` shall accept an optional `context` parameter (string, e.g., `"project:zoom"` or `"project:zoom,profile:professional"`). When provided, ambient scope is set for that tool call and any nested service operations. The parameter is optional; omitting it uses ambient scope from the transport layer or global scope.

### 5.9 Project and Entity Management

**FR-P-001** The system shall maintain a `projects` table with: `slug`, `display_name`, `build_system?`, `languages?[]`, `created_at`.

**FR-P-002** The system shall maintain an `entities` table with extracted named entities: `name`, `entity_type` (tool | project | person | pattern | concept | decision), `source_memory_id`.

**FR-P-003** The system shall maintain a `chunk_entities` relationship table mapping memory chunks to entities.

**FR-P-004** The structural pre-filter shall query `entities` and `chunk_entities` to constrain the search candidate pool before RRF ranking.

**FR-P-005** Entity extraction shall be performed asynchronously after memory ingest using the configured `ILlmClient` (or rule-based fallback).

### 5.10 System Health

**FR-H-001** `GET /health` shall return `200 OK` with body `{ "status": "healthy" }` when the application process is running.

**FR-H-002** `GET /ready` shall return `200 OK` when the database connection is confirmed and `503` when it cannot connect.

**FR-H-003** The system shall expose statistics via `GET /api/v1/stats`: total semantic memories, total episodic memories, total recall events, last consolidation run, database file size.

**FR-H-004** All structured application log entries shall include timestamp, log level, correlation ID, and component name.

## §6. Non-Functional Requirements

### 6.1 Performance (NFR-P)

**NFR-P1** Hybrid search (BM25+Vector via RRF, post-MMR) shall return a response in < 100 ms (p95) on up to 100,000 memory records on a local machine.

**NFR-P2** Structural pre-filter overhead shall add < 10 ms to hybrid search latency.

**NFR-P3** Per-ingest synthesis (view update) shall **not** block the memory write response; synthesis runs asynchronously via domain event.

**NFR-P4** Storyboard state reads and writes (status transitions, story list retrieval) shall complete in < 50 ms.

**NFR-P5** FTS5-only search (degraded mode, no embeddings) shall complete in < 5 ms on 100,000 records.

### 6.2 Storage (NFR-S)

**NFR-S1** Storage shall be backend-agnostic via the `IMemoryStore` abstraction. SQLite is the v1.0 default; PostgreSQL/Supabase is a first-class supported upgrade path, configured via `appsettings.json` (`Storage:Backend`).

**NFR-S2** The SQLite database file shall not exceed 1 GB for three years of moderate usage (projected: ~570 MB for ~310,000 records including embeddings at 1,536 dimensions).

**NFR-S3** The database shall be created automatically on first application run with zero manual configuration.

**NFR-S4** Backup shall be achievable by a single file copy (`.backup` command or OS copy in WAL-off mode).

**NFR-S5** Default database path: `~/.ai-memory/memory.db`; overridable via environment variable `AI_MEMORY_DB_PATH` or `appsettings.json`.

**NFR-S6** Structural pre-filter data (entities, relationships, chunk-entity mappings) shall be stored co-located in the same database as memories. No separate graph database is required in v1.0.

**NFR-S7** SQLite shall operate in WAL mode (`journal_mode=WAL`, `busy_timeout=5000`, `synchronous=NORMAL`, `cache_size=-64MB`, `mmap_size=268435456`).

### 6.3 Cost (NFR-C)

**NFR-C1** The system shall operate at €0/month when configured with local models (SQLite + Ollama for embeddings and synthesis). This is the mandatory baseline capability.

**NFR-C2** The combined cost of all optional cloud services (cloud database, cloud LLM/embedding API) shall not exceed **€10/month** when measured at the system's full 100,000-memory workload with 50 queries/day and 10 synthesis operations/day.

### 6.4 Local-First and Privacy (NFR-L)

**NFR-L1** The system shall operate fully offline. No feature shall require an active internet connection except the optional embedding service and optional LLM synthesis service.

**NFR-L2** No memory data shall leave the local machine by default. Cloud sync is only possible via user-configured and explicitly opt-in cloud backup.

**NFR-L3** The REST API shall bind to `localhost` (127.0.0.1) only by default.

**NFR-L4** No authentication or authorisation is required in the default single-user local deployment. API key / auth shall be implemented when multi-user mode is introduced.

### 6.5 Code Quality (NFR-Q)

**NFR-Q1** All four static analysers shall run on every `dotnet build` with `TreatWarningsAsErrors=true`:
- `Microsoft.CodeAnalysis.NetAnalyzers`
- `StyleCop.Analyzers`
- `SonarAnalyzer.CSharp`
- `Meziantou.Analyzer`

**NFR-Q2** All `PackageReference` entries shall use exact version pinning. No floating (`*`) or range (`[1.0,2.0)`) versions.

**NFR-Q3** CVE-flagged NuGet packages shall be updated within 48 hours of public disclosure.

**NFR-Q4** Code coverage (Cobertura XML) shall be collected on every `dotnet test` run but shall not gate the build in Phase 1. A coverage threshold shall be introduced after ST-007 establishes the baseline.

**NFR-Q5** Analyser suppressions shall be documented in `.editorconfig` with a dated justification comment. Blank suppressions without rationale are not permitted.

### 6.6 Deployment and Operations (NFR-D)

**NFR-D1** The system shall run as a Windows native service with zero external service dependencies at startup (no database server, no vector engine, no message broker). All dependencies are either in-process or optional.

**NFR-D2** The system shall support 1–5 concurrent MCP/REST client sessions without observable performance degradation. SQLite WAL mode provides concurrent reads; writes are serialised.

**NFR-D3** Embedding service unavailability (network failure, API error) shall degrade the search path gracefully to FTS5-only (BM25) results without returning an error to the caller. The response shall include a `degraded: true` flag in the metadata.

**NFR-D4** Storyboard view output shall be Obsidian-compatible: standard Markdown with YAML frontmatter properties queryable via the Dataview plugin.

**NFR-D5** All timestamps in API responses and database records shall use ISO 8601 format (UTC). All IDs shall use ULID format.
