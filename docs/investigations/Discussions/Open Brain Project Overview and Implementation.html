Short answer: The “Open Brain Project” you’re referring to is an open, user‑owned AI memory architecture built around Postgres + pgvector + MCP (Model Context Protocol). It provides a persistent, AI‑readable memory layer that any LLM can plug into without SaaS lock‑in.

Below is a clear, implementation‑focused breakdown so you can evaluate whether to use it as‑is or build your own version.

🧠 What the Open Brain architecture actually is

The Open Brain system is defined as an AI‑integrated memory layer:

  • A Postgres database with pgvector stores embeddings of your notes, thoughts, documents, and metadata.

  • MCP (Model Context Protocol) acts as the universal interface that lets any AI agent (Claude, ChatGPT, Cursor, etc.) query your memory.

  • Local or self‑hosted components ensure your data stays under your control, avoiding SaaS intermediaries.

  • Semantic search replaces manual tagging or folder structures. AI retrieves context based on vector similarity.

This is fundamentally different from “second brain” tools like Obsidian or Notion, which are human‑centric and require manual retrieval. Here, the memory is machine‑first.

🏗️ Core implementation components

1. Database layer (Postgres + pgvector)

  • Stores embeddings in a memories table.

  • Uses HNSW indexes for fast vector search.

  • Can run extremely cheaply (as low as ~$0.30/month depending on hosting).

2. MCP server

  • Exposes your memory to AI tools via a standard protocol.

  • Decouples your data from any specific LLM provider.

  • Lets you switch models without migrating data.

3. Embedding models (local via Ollama)

  • Default: nomic-embed-text for embeddings.

  • Optional: a metadata LLM (e.g., Qwen2.5 32B) for richer extraction.

4. Local infrastructure

The official installation uses:

  • Docker for Postgres + pgvector

  • Python MCP server

  • Ollama for embeddings

  • Optional dashboard for monitoring

🧪 Setup complexity (realistic view)

The official guide claims ~15 minutes to get running, but the real work is in:

  • Designing your ingestion pipeline

  • Deciding what to store

  • Managing embeddings and metadata

  • Ensuring safe context retrieval

🔧 When you should use Open Brain as-is

Choose this if you want:

  • A ready-made, well‑architected memory layer

  • MCP compatibility out of the box

  • Local embeddings without cloud dependencies

  • A system that works with Claude, ChatGPT, Cursor, etc. immediately

🛠️ When you should build your own

Build your own if you need:

  • A custom schema (e.g., hierarchical memory, temporal decay, multi‑agent memory)

  • A different vector store (Weaviate, Milvus, Pinecone, Qdrant)

  • A custom ingestion pipeline (e.g., event‑driven, multimodal, streaming)

  • Integration with your own agents or tools

  • Stronger privacy guarantees (air‑gapped, offline‑only)

If you want structural similarity search in your “Open Brain–style” memory system, you’re essentially asking for a second retrieval dimension beyond embeddings:

  • Semantic similarity → via embeddings (pgvector)

  • Structural similarity → via graph‑ or pattern‑based matching

This is absolutely doable, but it requires extending the architecture. Here’s the cleanest way to add it without breaking the simplicity of the Open Brain approach.

🧠 Structural similarity: what it means in this context

There are three common interpretations of “structural similarity” in memory systems. You need to pick which one you want:

1. Document structural similarity

Similarity based on layout or structure, e.g.:

  • headings

  • bullet patterns

  • code structure

  • JSON schema

  • argument structure

Useful for: codebases, technical notes, logs.

2. Knowledge‑graph structural similarity

Similarity based on relationships, not text:

  • entities

  • edges

  • graph neighborhoods

  • subgraph isomorphism

Useful for: reasoning, agents, multi‑step workflows.

3. Embedding‑augmented structural fingerprints

Hybrid:

  • LLM extracts a structural “fingerprint”

  • You store it as a vector

  • You search both semantic and structural vectors

Useful for: fast, simple implementation.

🏗️ How to add structural similarity to an Open Brain–style system

Below is the architecture that fits best with your technical style (Postgres, pgvector, MCP, local models).

Option A — Add a second pgvector column for structural embeddings (easiest)

This is the most practical and keeps everything inside Postgres.

How it works

  1. When ingesting a memory item:

    • Generate semantic embedding (normal)

    • Generate structural embedding using a structure‑focused model

      • e.g., nomic-embed-text for semantics

      • and jina-embeddings-v3-code or bge-m3 for structure

  2. Store both in the same row:

Code
id | content | semantic_vec | structural_vec | metadata

  1. At query time:

    • Run two searches

    • Combine scores (weighted sum or max)

Pros

  • Minimal changes

  • Fast

  • Works with MCP immediately

  • No new infrastructure

Cons

  • Structure is approximated, not explicit

  • Not ideal for graph‑like reasoning

Option B — Add a graph layer (Neo4j or Postgres + pg_graph)

This gives you true structural similarity.

How it works

  1. Use an LLM to extract entities + relations

  2. Store them in a graph DB

  3. Use graph algorithms:

    • Jaccard similarity

    • Graph embeddings

    • Subgraph matching

  4. Combine graph similarity with semantic similarity

Pros

  • Best for reasoning

  • Enables multi‑hop memory

  • Enables agent workflows

Cons

  • More infra

  • More ingestion complexity

Option C — Structural fingerprints (my recommended hybrid)

This is the sweet spot for your use case.

How it works

  1. LLM generates a structural fingerprint, e.g.:

Code
{
  "type": "procedure",
  "steps": 5,
  "entities": ["SolarEdge", "inverter", "backup"],
  "complexity": "medium",
  "topics": ["power", "compliance"]
}

  1. Convert this JSON into a vector using a small embedding model

  2. Store it in a structure_vec column

  3. Query both semantic and structural vectors

Pros

  • Very flexible

  • No graph DB needed

  • Works with any content type

  • Easy to tune

Cons

  • Requires a fingerprinting prompt

  • Slightly more ingestion work

🔍 How retrieval works with both dimensions

Query pipeline

  1. User asks: “How do I upgrade my SolarEdge inverter for backup power?”

  2. System generates:

    • semantic embedding

    • structural fingerprint embedding

  3. Run two searches:

Code
SELECT * FROM memories
ORDER BY
  0.7 * (semantic_vec <-> query_semantic_vec) +
  0.3 * (structural_vec <-> query_structural_vec)
LIMIT 10;

  1. MCP returns combined results to the LLM

  2. LLM synthesizes the final answer
